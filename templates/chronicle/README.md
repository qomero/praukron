# Praukron project chronicle

This directory is shared project memory for people and agents. The product
specification describes what was intended; this chronicle records what is true
now. It should explain the project before anyone reads implementation code.

Praukron means Project Chronicle: a common language for understanding purpose,
historical decisions, current state, and future work. Use it for discussion,
review, advice, and continuity between people as well as agents.

## Authored and compiled

```text
.praukron/chronicle/   authored by people and agents; the only source of truth
                      (except INDEX.md, which Praukron generates, and
                      RESPONSES.md, which `praukron respond` appends to;
                      archive/<phase>/ holds closed phases' tasks, contracts,
                      assumptions, debt, trace events and journal entries,
                      moved there by `praukron archive`, and is authority like
                      the rest; RESPONSES.md, COORDINATION.md and ADR/ are
                      never archived)
.praukron/compiled/    compiled by Praukron; safe to delete and regenerate
```

Nothing in `.praukron/compiled/` is authoritative. Delete it and recompile and
no project fact is lost. Never hand-edit it, and never let a generated view decide a
question that an authored document answers.

## Read order

1. `INDEX.md` first: the generated map of what matters now and where each
   record lives. Then only the records it points to; `praukron retrieve`
   returns them with their sources.
2. `.praukron/compiled/STATE.md` for the current position and the product
   thesis.
3. `PHASES.md` for the active phase, its exit conditions, and gate status.
4. `.praukron/compiled/TASK_GRAPH.md` for in-flight, ready, and blocked work.
5. The selected entry in `TASKS.md`, and its module in `MODULES.md`; the
   module names the phase. `praukron context <task>` gives the lineage.
6. Its contract in `ACCEPTANCE.md`.
7. Its governing entries in `ADR/`.
8. `INTENT.md` for the single task in progress.
9. `HANDOFF.md` for current implementation continuity, and the task's brief in
   `COORDINATION.md` when a coordinator runs the work.
10. Recent `JOURNAL.md` entries when further detail is needed.
11. Read `THESIS.md`'s source, specifications, or code only when the selected
    task requires them.

## Authority

- `THESIS.md` is the product thesis: the one statement every phase, module,
  and task descends from.
- `PHASES.md` is phase outcome, entry, exit, exit authority, and status.
- `MODULES.md` is module identity, outcome, and the one phase (or `P-NONE`) each
  module belongs to.
- `TASKS.md` is task identity, module, domain, dependency, ownership, execution
  state, validation state, contract reference, and evidence.
- `ACCEPTANCE.md` is the completion contract. A task is not done because someone
  says it is done; it is done when its frozen contract has sufficient evidence.
- `INDEX.md` is generated by `praukron compile` and is not authority. It routes
  an agent to the records that matter now; never edit it.
- `ADR/` is accepted decision authority, one file per ADR, append-only.
- `INTENT.md` is overwritten and holds zero or one current task.
- `HANDOFF.md` is overwritten and holds current implementation continuity.
- `JOURNAL.md` is append-only history, not product or acceptance authority.
  An entry may name ranges: `T-P0-01..05`, `T-P0-01..T-P0-05` and
  `ADR-003..005` name each id they span (same stem, same tail width, at most
  100 ids). `validate` warns about members that do not exist and about a range
  it cannot read; an entry moves to an archive only when every member has.
  Its authored bytes and observed same-date order govern the ordering sidecar.
- `archive/JOURNAL.order.json` remembers the order of unique journal headings
  across files (ADR-072). Commit it with the archive; never hand-edit it or
  discard it as a compiled view. Observed same-date order in a journal wins;
  archive/restore update the metadata in their transaction. `validate` warns
  about drift and duplicates. Missing or incomplete cross-file ties keep only
  affected journal entries, with repair instructions; other records can move.
  An absent working heading is new and keeps its same-date working neighbours;
  it follows known ties only without a known same-date working constraint.
  An absent archived heading is lost history and holds its date. Saved names on
  held dates survive unrelated metadata rewrites, including renamed/removed names.
  After a heading rename or lost sidecar, recover matching headings/order from
  Git history or `.praukron/backup/<timestamp>/`, preserving later edits. If
  every date is wholly in one journal, remove the broken sidecar and
  the next journal move safely rebuilds it. The first backup may contain only
  the original journal, since its sidecar did not yet exist. See the guide's
  “Journal ordering and repair” section for chronology and recovery limits.
- `TRACE.md` is append-only operational evidence: tool calls, commands,
  mini-actions, mutations, failures, retries, and validation runs. It holds no
  authority and never counts as progress.
- `TECH_DEBT.md` is the register of known technical debt: what each compromise
  costs, its trigger, and its exit condition. A debt is a liability, not a task.
- `ASSUMPTIONS.md` is the register of provisional agent assumptions. An
  assumption holds no authority; the records it is applied in do.
- `RESPONSES.md` is the owner's input, verbatim and append-only. Agents read and
  reconcile it and never edit it. `By:` is the active GitHub CLI login, never a
  typed name; an agent never issues `VERIFY`.
- `COORDINATION.md` is optional: a coordinator's standing conventions
  (`## CV-<id>`) and one brief per task (`## BR-<id>`), so that how agents are
  run survives the loss of any session (ADR-075). It is authority below
  contracts, invariants and ADRs; a brief adds to its task's contract and
  never changes a criterion. `context <task>` and `retrieve <task>` carry the
  task's brief and the conventions it rests on; `context <task> --role
  coordinator` gives a coordinator its own. It is never archived, and a
  task with an `ACTIVE` brief stays in the working files.
- `.praukron/compiled/STATE.md` and `.praukron/compiled/TASK_GRAPH.md` are
  views. They report authority and never override it.

## Working rules

1. Record every new work request as a task before implementation without waiting
   for a Praukron command. Give it a `Module:` from `MODULES.md`; its phase
   comes from that module, never from the task. If no module fits, author one
   in a phase or `P-NONE` first. Give it a `Domain:` — `execution` for work that advances the project itself,
   `operations` for work that maintains the environment it is built in
   (tooling, upgrades, CI, housekeeping). Changing a task's domain is a
   material decision: record it in the journal, or in an ADR when it changes
   what the project counts as progress.
2. Work on one task at a time. Mark it `WIP`, record owner and claim date, and
   keep the exact execution point in `INTENT.md`.
3. Hard dependencies come from `TASKS.md`. Label suggested ordering as a
   suggestion; do not silently turn it into a dependency.
4. A contract freezes when its task becomes `WIP`. Change it only through an
   accepted Acceptance Change Request (`praukron acr add` records one; the
   owner decides it). A reviewer preference is not a criterion. `task update`
   records the task's `Frozen:` fingerprint, and `validate` reports a frozen
   criterion edited without an accepted request; never edit the fingerprint.
5. Mark a task `DONE` only when every mandatory criterion in its contract holds
   and its evidence is recorded. Keep completion separate from validation
   strength: `UNTESTED`, `SYNTHETIC`, `AI_REVIEWED`, or `HUMAN_VERIFIED`.
6. Only a named human may record `HUMAN_VERIFIED`, and only against `MANUAL`
   evidence.
7. Append an ADR as soon as a material choice is made, accepted, or acted on.
   When a decision changes, supersede the earlier ADR and preserve its file.
8. Update `HANDOFF.md` and append a `JOURNAL.md` entry before leaving work
   mid-air. `Left mid-air` and `Next` must be explicit even when the answer is
   "nothing."
9. Append an event to `TRACE.md` when an action could later explain a failure,
   a blocked gate, or a regression. Never record secrets or private reasoning.
10. When a choice has no answer in authority, record it in `ASSUMPTIONS.md`
   before relying on it, unless the assumption policy reserves it; a reserved
   choice becomes an `Authority: owner` task. Reconcile every owner response in
   `RESPONSES.md` and never edit one.
11. Keep entries concise. Put product rules in the specification and durable
    implementation choices in ADRs, not in the session diary.
12. A coordinator that runs other agents records its conventions and each
    task's brief in `COORDINATION.md` before starting an agent on the task,
    points the agent at the task rather than at files outside the chronicle,
    keeps the brief's review round current, and closes the brief when the task
    is merged or abandoned. Edit one section, then run `validate`.

## Checkpoint trigger

Update the chronicle while working. Early enough to finish writing, checkpoint
before a handoff, interruption, compaction, or any known or estimated agent or
host context, token, time, session, rate, or quota limit:

1. update task status, validation, criterion state, evidence, and governing ADRs;
2. synchronize the compiled views;
3. update or clear the single intent;
4. rewrite `HANDOFF.md` and append a journal entry with the exact next action.

If the host cannot report its limits, checkpoint after meaningful milestones,
before long-running work, and before ending. Do not wait until the last message.

## Entry modes

These modes initialize a fresh chronicle. If records already exist, preserve
them and resume; neither mode resets history.

- **New repository:** find or elicit the product thesis first, then derive
  phases, modules, tasks, and contracts from it and the product specification
  with the developer, in that order. Record material decisions as ADRs.
- **Existing repository:** start with an empty chronicle and record from the
  current session onward. Do not reconstruct historical tasks or decisions.
